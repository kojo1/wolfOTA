## wolfOTA --- OTA cloud service for secure update

[English](README.md) | 日本語

wolfOTAはデバイスのファームウェアを安全に更新するためのクラウドサービスです。このサービスのためのデバイス上のプラットフォームを含みます。
実装にはできるだけwolfSSLの製品を利用します。

### 利用シナリオ

- インストール：セキュア化されていないデバイスに、セキュアアップデートの機能(wolfOTA for Device: o4d)を追加する。
- エンロール：セキュアアップデートの機能を追加したデバイスをwolfOTAのクラウドサービスに登録する。
- 初期アテステーション: エンロール時に正しいo4dが動作していることを遠隔で確認する。
- 証明書更新(再エンロール)：有効期限が近づいたデバイス証明書をESTで更新する。
- デプロイ：新しいバージョンのファームウェアをエンロールしているデバイスに配布する。
- 遠隔アテステーション: 任意のタイミングで、デバイス上で正しいファームウェアが動作していることを遠隔で確認する。
- 隔離：アテステーションに不合格となったデバイスを隔離する。
- アンエンロール：エンロールされているデバイスを対象から解除する。

### 主な機能とコンポーネント

クラウド側

- デプロイサーバ：MQTTベースのサーバ(wolfMQTT broker または mosquitto、wolfSSLによるmTLS)
- エンロールサーバ：エンロール時、証明書更新時にESTにて証明書を発行する。
  オープンソースのESTサーバ globalsign/est(Go, MIT)を使用する。wolfCertとの相互接続はwolfCertのinterop試験で確認済み。
  発行処理は`est.CA`インターフェース(`Enroll` / `Reenroll`)を実装して組み込み、そこで検証サーバの判定を確認する。
  (wolfCert付属のサーバは開発・相互接続試験用のため、単体試験にのみ使用する。)
- 検証サーバ(Verifier)：デバイスから送られたアテステーショントークンを検証し、
  基準値(Reference Value)と照合して判定結果をデバイス台帳に記録する。
- デバイス台帳：デバイスID、証明書、DeviceID公開鍵、ファームウェアバージョン、
  アテステーション結果、状態(enrolled / quarantined / revoked など)を管理する。

デバイス側(o4d)

- wolfCert(github.com/wolfssl/wolfcert)を使ったクライアントサイドのエンロール、証明書更新機能
  (Zephyrモジュールとして組み込み、鍵操作はCryptoCb経由でELSに委譲)
- wolfBootによるセキュアブート、更新機能
- 遠隔アテステーション機能(wolfBoot DICE、トークンはwolfCOSEによるCOSE_Sign1)
- 更新エージェント(wolfMQTTによる受信、更新パーティションへの書き込み)
- アンエンロール機能

### 信頼の前提(Root of Trust)

o4dを後からインストールする場合、初期アテステーションで「正しいo4dが動いている」と
言える根拠は、デバイスのハードウェアRoTに依存する。将来的には以下のバリエーションをカバーする。

| 種別 | 内容 | 例 |
|---|---|---|
| A. UDSあり(ハードウェア保護) | UDS/CDI/鍵がソフトウェアから見えない | NXP MCX N (ELS) |
| B. UDSあり(ソフトウェアから読める) | wolfBootがソフトウェアでDICE導出 | STM32H5 |
| C. TPM | wolfTPMによるmeasured boot、Quote | 外付けTPM, fwTPM |
| D. ハードウェアRoTなし | 工場プロビジョニング、またはTOFU(初回接続時の信頼) | 汎用MCU |

**初期PoCはA(UDSありのチップ)から始める。** 対象はNXP FRDM-MCXN947のELS(EdgeLock Secure Subsystem)。

- ブートROMがUDSとwolfBootのハッシュから初期CDIをELSのキースロットに生成する。
- wolfBootがELSのHKDFでCDIを導出し、鍵生成・署名をELS内で行う。
- 秘密値(UDS/CDI/秘密鍵)はソフトウェアに露出しない。

#### 実装ポリシー

汎用部分をできるだけ共通に保ち、チップ個別に提供されている機能はそれを利用する。

- CBOR/COSEエンコード、トークン形式、通信プロトコル、サーバ側は共通実装とする。
- CDI導出、鍵生成、署名などのRoT依存処理はwolfBootのHALフック
  (`hal_dice_update_cdi()` / `hal_dice_create_attest_key()` など)の背後に置き、
  チップ固有の用語・APIはHAL実装の外に出さない。
- チップ側に機能がない場合はwolfCryptによるソフトウェア実装にフォールバックする。

### アテステーション鍵の構成(DICE 2層)

ファームウェアを更新するたびにアテステーション鍵が変わると、検証サーバに登録した公開鍵で
検証できなくなる。これを避けるため、DICEを2層構成とする。

| 層 | CDI | 鍵 | 依存する測定値 | 寿命 |
|---|---|---|---|---|
| Layer 0 | CDI_L0 = f(UDS, wolfBootの測定値) | DeviceID鍵 | wolfBoot | 長期(wolfBootを更新しない限り不変) |
| Layer 1 | CDI_L1 = HKDF(CDI_L0, アプリケーションイメージの測定値) | Alias鍵 | wolfBoot + アプリケーション | ファームウェアごと |

- wolfBootが起動時にDeviceID鍵でAlias鍵の証明書(Alias証明書)に署名する。
  Alias証明書にはアプリケーションイメージの測定値を含める。
- アテステーショントークンはAlias鍵で署名し、Alias証明書を添付する。
- 検証サーバはエンロール時に登録したDeviceID公開鍵で
  「DeviceID → Alias証明書 → トークン」の連鎖を検証する。
- ファームウェアを更新してもDeviceIDは変わらないため、検証サーバの登録内容を更新する必要はない。
- 現行のwolfBoot DICEは単層(IAK)であり、2層化はPoCでの開発項目とする。

### エンロールと初期アテステーション

1. デバイスが検証サーバからnonceを取得する。
2. デバイスがnonceを含むアテステーショントークン(EAT, COSE_Sign1)を生成する。
3. デバイスがwolfCertでデバイス鍵(TLS用)を生成してCSRを作り、エンロールサーバへEST `/simpleenroll` で送る。
   CSRにはトークンを独自OIDの拡張として格納する(wolfCertの`customize`コールバックで追加)。
4. 検証サーバがトークンを検証(Alias証明書の連鎖、nonce、測定値と基準値の照合)する。
5. 検証に合格した場合のみ、エンロールサーバが証明書を発行し、DeviceID公開鍵と共にデバイス台帳に登録する。

- トークンをCSRの中に入れることで、CSRの署名によりトークンとデバイス鍵が結び付く。
- エンロールサーバは`/csrattrs`(`est.CA`の`CSRAttrs`)でこのOIDを要求する。
- エンロールサーバは`Enroll`の中でCSRからトークンを取り出して検証サーバに問い合わせ、合格時のみ発行する。
- RFC 7030のtls-uniqueによるCSRとTLSセッションの結び付けはwolfCertが未対応(TLS 1.3にtls-uniqueが無い)。

### 証明書更新(再エンロール)

1. デバイス(wolfCert)が証明書の残り有効期間を確認し、しきい値を下回ったら更新を開始する。
2. 現在のデバイス証明書によるmTLSでエンロールサーバに接続し、EST `/simplereenroll` で新しいCSRを送る。
   アテステーショントークンを添付し、検証サーバの判定に合格した場合のみ発行する。
   エンロールサーバ側は`Reenroll`の中で、mTLSで提示された現行証明書とCSRの照合、台帳上の状態確認、トークンの検証を行う。
3. 新しい証明書を保存し、以降の接続で使用する。旧証明書は有効期限まで残るが、台帳上は旧版として扱う。
4. CA証明書の更新はEST `/cacerts` で取得する。
5. 隔離中・失効済みのデバイスからの再エンロールは拒否する。

### デプロイ

基本的にwolfBootのツールとMQTTのpub/subで構成する。

1. 署名：wolfBoot keytools(`sign`)でファームウェアに署名し、バージョンを付与する。
2. 通知：デプロイサーバが対象デバイスのトピックにマニフェスト(バージョン、サイズ、ハッシュ、チャンク数)をpublishする。
3. 分割転送：署名済みイメージをチャンクに分割してpublishし、デバイスはsubscribeして受信する。
   チャンクには通し番号を付け、デバイスは受信状況(ack / 再送要求)をpublishする。
4. 書き込み：更新エージェントが受信したチャンクをwolfBootの更新パーティションに書き込む。
5. 適用：全チャンク受信後に`wolfBoot_update_trigger()`を呼ぶ。**更新は次回再起動時をデフォルトとする。**
6. 確認：wolfBootが署名とバージョンを検証して起動する。新ファームウェアは起動確認後に`wolfBoot_success()`を呼び、
   確認できない場合はwolfBootがロールバックする。
7. 報告：デバイスが新しいバージョンとアテステーショントークンをpublishし、デバイス台帳を更新する。

トピック構成(案)

```
wolfota/<device-id>/manifest   サーバ → デバイス
wolfota/<device-id>/chunk      サーバ → デバイス
wolfota/<device-id>/status     デバイス → サーバ (ack, 再送要求, バージョン報告, 失敗報告)
wolfota/<device-id>/attest     双方向 (nonce要求 / トークン)
wolfota/<device-id>/control    サーバ → デバイス (アンエンロールなど)
```

#### 更新失敗時の扱い

イメージの検証、スワップ中の電源断からの復旧、起動確認がない場合のロールバックはwolfBootの状態管理に含まれる。
それ以外の以下のケースをo4dとサーバ側で扱う。

| ケース | 対応 | 担当 |
|---|---|---|
| 転送の中断(通信断、デバイス再起動) | 受信済みチャンクを記録し、途中から再開する | 更新エージェント、デプロイサーバ |
| 受信イメージの不整合 | `wolfBoot_update_trigger()`の前にマニフェストのハッシュと照合し、不一致なら破棄して報告する | 更新エージェント |
| 新ファームウェアがハングし`wolfBoot_success()`にも再起動にも至らない | ウォッチドッグを有効にし、リセットでロールバックさせる | o4d(ボード設定) |
| 起動はするがサービス不能(MQTTに再接続できない等) | `wolfBoot_success()`はサーバへの再接続とアテステーション合格後に呼ぶ | 更新エージェント |
| ロールバックの発生をサーバが知らない | 起動後に現在のバージョンを報告し、サーバが期待バージョンとの不一致を失敗として記録する | 更新エージェント、デプロイサーバ |
| 同じ版の再配布による失敗の繰り返し | 失敗した版は自動再配布しない(運用者の判断で再実行) | デプロイサーバ |
| 対象外のイメージ(別ボード・別パーティション) | マニフェストの対象ボード・イメージ種別を確認し、拒否する | 更新エージェント(wolfBootもイメージ種別を検証) |

#### ダウングレード攻撃の防止

- wolfBootは現在より小さいバージョンへの更新を拒否する(`ALLOW_DOWNGRADE`を無効とする既定設定を使用)。
- バージョンは署名済みのイメージヘッダに含まれるため、改ざんすると署名検証で拒否される。
- デプロイサーバもマニフェストの段階で旧バージョンの配布を拒否する。
- 物理アクセスによるフラッシュへの旧イメージ書き込みへの対策はPoCの範囲外とする。

### 遠隔アテステーション

1. 検証サーバが`attest`トピックでnonceを送る。
2. デバイスがwolfBootのアテステーションサービスでトークンを生成し、Alias証明書と共に返送する。
3. 検証サーバがDeviceID公開鍵(エンロール時に登録)でAlias証明書とトークンを検証し、測定値を基準値と照合する。
4. 基準値は、デプロイ時に署名したイメージのハッシュから登録する。

#### アテステーション不合格時の扱い(隔離)

デフォルトは隔離とする。

- 隔離されたデバイスは、デプロイ対象と証明書更新の対象から外す。
  `attest`・`status`・`control`トピックへのアクセスのみを許可する(ブローカのACL)。
- 再度アテステーションに合格するか、運用者が解除すると隔離を解く。
  隔離中に正しいファームウェアの再配布が必要な場合は運用者の判断で行う。

アテステーション結果の確認手段(簡易)

- 検証サーバはデバイスごとに、判定時刻、判定結果(合格 / 不合格 / 検証不能)、理由、
  報告された測定値とファームウェアバージョンを台帳に記録する。
- 運用者はCLI(またはHTTPの参照用エンドポイント)でデバイス一覧と最新結果、履歴を確認できる。

### PoCでの開発項目

既存製品で不足していて、PoCで開発が必要な項目。

| 項目 | 対象 | 内容 |
|---|---|---|
| DICE 2層化 | wolfBoot | DeviceID鍵とAlias鍵、Alias証明書の生成 |
| ELSでの公開鍵演算 | wolfSSL(NXP ELSポート) | 現行のELSポートのCryptoCbはAES/CMAC/ハッシュ/乱数のみ。ECC P-256の鍵生成・署名をELSのキースロットで行うCryptoCbを追加し、wolfCertの`key_id`(キースロット)に対応させる。完成までの暫定はソフトウェア鍵 |
| 発行処理(CA実装) | globalsign/est | `est.CA`を実装し、CSR内のトークンを検証サーバに問い合わせ、合格時のみ発行する。CA鍵・発行証明書は台帳と連携 |
| 更新エージェント | o4d | MQTT分割転送の受信、更新失敗時の扱い |
| 検証サーバ・デバイス台帳・デプロイサーバ | クラウド | 新規 |

### シミュレーション環境(Docker)

実機の前に、ホストPC上でdocker composeにより全体の流れを再現する。

| コンテナ | 内容 |
|---|---|
| `ca` | wolfCLUでCAとサーバ証明書を作成し、共有ボリュームに置く |
| `broker` | mosquitto(TLS 1.3, mTLS) |
| `est` | globalsign/estと独自の`est.CA`実装 |
| `verifier` | 検証サーバとデバイス台帳(Go, SQLite) |
| `deploy` | wolfBoot keytoolsによる署名とMQTT分割転送 |
| `device` | wolfBoot simターゲット + Linux版o4d(複数台に増やせる) |

- wolfBootのsimターゲットはフラッシュをファイルで模擬し、署名を検証してアプリケーション(o4d)を起動する。
  o4dはwolfCertでエンロールし、wolfMQTTで更新を受信して更新パーティションに書き込み、`wolfBoot_update_trigger()`を呼ぶ。
  再起動後、wolfBootがイメージを入れ替える。
- ELSは模擬できないため、シミュレーションではUDSをファイルから読むソフトウェア実装(信頼の前提B)を使う。
  これは「チップ固有の部分はHALの後ろに置く」方針の最初の実例であり、
  DICE 2層化はsimで先に開発・検証し、その後MCXN947のELS用HALに差し替える。
- wolfSSL製品はイメージのビルド時にタグ・コミットを固定してGitHubから取得する。

段階

1. CA、ブローカ、EST、デバイス：エンロールして証明書を取得し、mTLSでMQTTに接続する。
2. デプロイ(署名、分割転送、再起動による更新、ロールバックの確認)。
3. 検証サーバ、DICE 2層化(simのHAL)、トークン付きエンロール、隔離。
4. 証明書更新とアンエンロール。

ディレクトリ構成

```
docker-compose.yml
docker/      ベースイメージ(wolfSSL, wolfCLU, wolfMQTT, wolfCert)
cloud/       ca, broker, est, verifier, deploy
device/      o4d と wolfBoot sim の設定
```

#### 第1段階の実行方法

```sh
docker compose build base          # wolfSSL 5.9.4 + wolfCLU + wolfMQTT + wolfCert(初回のみ)
docker compose up -d --scale device=3
docker compose logs -f device
./scripts/phase1-test.sh           # エンロール、mTLS、ACL、拒否ケースの確認
docker compose down -v             # PKIを含めてすべて削除
```

- サービス名：`est.wolfota.test:8443`(EST)、`broker.wolfota.test:8883`(MQTT over mTLS)。
- デバイスIDは当面コンテナのホスト名(第3段階でDICE由来のIDに置き換える)。
- 初回エンロールは、トークン付きエンロール(第3段階)までの間、ブートストラップ用のHTTP Basic認証を使う。

#### 第1段階で判明した注意点

- wolfCertは単一ラベルのホスト名(`est`)を拒否する(wolfSSLを`WOLFSSL_ALLOW_SINGLE_LABEL_HOSTNAME`付きでビルドしない限り)。そのためサービスはFQDNの別名を使う。
- wolfMQTTのTLSコールバックは0ではなく`WOLFSSL_SUCCESS`(1)を返す必要がある。
- wolfCLU v0.2.0：`ca`は設定ファイルに`[ca]`セクションが必要(無いとクラッシュする)、`-out`は`new_certs_dir`からの相対パスで出力される、設定ファイルの`extendedKeyUsage`に未対応。
